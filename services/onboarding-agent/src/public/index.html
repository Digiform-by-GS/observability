Onboarding Agent

Submit a GitHub or GitLab repository. An agent instruments it for the observability platform and returns a patch, or opens a pull/merge request.

What this agent supports
StackRequiresWhat you get
Node.js ^18.19.0 || >=20.6.0
ESM only — needs "type": "module"		 Traces, metrics, and logs correlated to their trace. Express, Fastify, plain HTTP.
Go 1.25+
required by OpenTelemetry v1.44		 Traces, metrics, and slog logs carrying trace context. Routers: chi, gin, echo, gorilla/mux.
Next.js 15+ Server-side rendering traces only. No logs — the Next integration does not emit them.
Browser / RUM any modern browser Page-load traces, Core Web Vitals, JS errors. Needs a browser ingest endpoint on the platform.

Not supported: Python, Java, Ruby, PHP, .NET. If the repository is none of the above, the agent will report "nothing to onboard" rather than guess — that is a correct result, not a failure.

Already instrumented? Submit it anyway. The agent detects existing instrumentation, leaves your service name alone, and reports what is missing instead of redoing the work.

Where this service gets its environment variables

The agent only sees this one repository, on one branch. If the live config is somewhere else, it cannot tell — and a repo often still contains deployment files that look current but are dead. Answering here is what turns “set these variables somewhere” into an instruction someone can act on.

What to wire

Traces and metrics are always included — they come from a single SDK initialisation, so there is no such thing as one without the other. These two are genuine choices.
